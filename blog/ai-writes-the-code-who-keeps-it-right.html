AI writes the code. What keeps it right six months later?

Every software team builds with AI now, and the first weeks always look fast. The difference between teams shows around month three, when the product is large, every AI session starts with no memory of the last one, and the code quietly stops following its own rules.

What drift looked like on a real product

We measured a large product that we deliver with AI: more than 40 batches of work and about 300 server-side actions at the time. The findings were uncomfortable.

  • The architecture document listed six rules marked as enforced. Nothing actually ran them.
  • The code style checker had stopped working after a framework upgrade. It stayed broken for weeks, and nobody noticed, because nothing ran it either.
  • The same small helper functions had been written again and again, in file after file.
  • The one rule that never drifted was the one built into the code itself, so that breaking it was impossible instead of forbidden.

The cause was not careless people. Each piece of work was done by a fresh AI session that knew only what the files in front of it said. A rule that lives in a document the session never opens does not exist.

Three layers, each covering the others

  1. The right way is the easy way. Shared building blocks sit where a session reaches first, so the obvious choice is also the correct one.
  2. A machine checks every change. A script counts the things that must not grow: duplicated helpers, oversized files, shortcuts around the access checks. The numbers are stored, and a change that raises any of them is refused. They can only go down.
  3. The rules are written where the AI reads them. Every task prompt carries the same closing line: which checks must pass and what proof to show before the work counts as done.

Decisions belong to people, before the build

Every real choice in a batch of work becomes a short card: the question, a recommended answer, the alternative and the evidence. The client rules on the cards before any code is written. If the AI meets a new choice in the middle of a task, it stops and raises a card. It never decides inside the code.

Done means shown

A task is finished when its proof exists: the automated checks, a scripted walk through the real screens, and screenshots that someone has opened and read. We learned that last part the hard way. A test can pass on a screen that looks broken to any person who glances at it.

Five questions for any team that builds for you with AI

  1. What stops the tenth AI session from undoing the rules the first one followed?
  2. Which of your rules are checked by a machine on every change, and which only live in a document?
  3. Who decides when the AI finds two ways to build something, and when do they decide?
  4. What do you show me as proof that a piece of work is done?
  5. Where do the lessons of this project go, so the next one starts with them?

Speed with AI is now available to everyone. A product that is still easy to change after a year is not, and that comes from the engineering around the model. That is the part we sell.
